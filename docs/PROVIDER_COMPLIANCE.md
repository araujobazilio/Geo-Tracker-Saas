# Provider Integration Compliance

> **Official provider docs last verified:** 2026-08-19

This document defines the compliance and methodological rules governing provider
integrations in GEO Tracker. It is normative: every provider adapter, the Scan
Engine, and any reporting surface MUST conform to the constraints below.

---

## 1. Google Compliance Boundary (CRITICAL)

The Google Interactions API surface available to GEO Tracker is **MODEL_ONLY**.
This is **NOT** the same as Google AI Overviews measurement.

- **Google Search grounding is disabled** in the Google adapter.
- **Reason:** Current Google API / Google Search grounding terms impose
  restrictions that conflict with GEO Tracker's planned automated storage and
  analysis of grounded results.
- **Phase 5:** `GoogleProviderAdapter` supports `MODEL_ONLY` only.
- If `request.mode == WEB_GROUNDED`: raise
  `ProviderModeNotAllowedError` **before any network call** is made.
- **Error message:**
  > "Google Search grounding is disabled for this provider surface."
- Any future implementation that enables grounding requires a **separately
  reviewed compliant path**; it must not be enabled by default or behind a flag
  without that review.

### Adapter surface (Phase 5.1)

- The adapter now uses the **Interactions API** (`POST /v1beta/interactions`),
  **NOT** `generateContent`.
- `store=false` for stateless one-shot measurements (no server-side session
  persistence).
- Thought/reasoning steps are **discarded** — only `model_output` text is
  exposed.

### Labeling

| Field   | Value                    |
|---------|--------------------------|
| Provider | `GOOGLE`                |
| Surface  | `GOOGLE_INTERACTIONS_API` |
| Mode     | `MODEL_ONLY`            |

> **This does NOT equal:** Google AI Overviews.

---

## 2. Methodology — Provider Surface Distinction

API results are measurements of their **named provider surfaces**, not of any
consumer product or UI. This distinction is essential for trustworthy reporting.

- `OPENAI_RESPONSES_API` **!=** consumer ChatGPT UI
- `ANTHROPIC_MESSAGES_API` **!=** Claude.ai UI
- `GOOGLE_INTERACTIONS_API` **!=** Google AI Overviews
- `PERPLEXITY_SONAR_API` **!=** every Perplexity consumer product mode

Reports and evidence records MUST label results by the provider surface actually
measured. They MUST NOT imply measurement of a consumer product that was not
queried.

---

## 3. No Hidden System-Prompt Distortion

For GEO measurement, the **user prompt itself is the experimental input**.

- Adapters may perform only the **minimum provider-specific envelope** required
  by the API (e.g., the request shape, required headers, role mapping).
- **No different semantic system prompts** for different providers.
- If a provider API requires a `system` / `instruction` field, **leave it absent
  or neutral** unless official API semantics require otherwise.
- This is a **methodological rule**, not a convenience: injecting provider-specific
  system prompts would invalidate cross-provider comparison.

---

## 4. Prompt Text Integrity

The prompt text sent to the provider MUST remain **EXACTLY** the `Prompt.text`
generated by the `PromptSet`.

- **No** automatic prepending of provider-specific SEO instructions.
- **No** "You are an SEO analyst", "Please mention sources", or "Include our
  brand".
- **No** provider-specific few-shot examples.
- **No** silent rewriting, trimming, or reformatting of the prompt text.

This preserves cross-provider measurement comparability. Any deviation — even
whitespace normalization of the prompt — is a compliance violation.

---

## 5. No Chain of Thought

Provider adapters MUST **NEVER** expose or persist private reasoning, thinking,
or chain-of-thought blocks.

- If an API returns separate reasoning/thinking content: **ignore it** for
  normalized results.
- Store **only**:
  - final answer text,
  - citations,
  - usage metadata,
  - request identifiers,
  - safe operational metadata.

Reasoning tokens, if billed, may be reflected in usage metadata totals but the
reasoning content itself MUST NOT be stored, logged, or surfaced.

---

## 6. API Key Security

API keys are **server environment configuration only**.

- Stored as `SecretStr` in Settings.
- **Never** persisted in the database in Phase 5.
- **Never** sent to the browser.
- **Never** included in `repr`, logs, or exceptions.
- BYOK (Bring Your Own Key) remains **deferred**.
- **No** provider-key API endpoints.

Any error path that would otherwise leak a key MUST redact it before it reaches
any log, exception message, or response body.

---

## 7. No Public Execution Endpoint

There is **no** public endpoint that triggers arbitrary provider execution.

- **No** `POST /api/provider/test`.
- **No** `POST /api/provider/execute`.
- **No** public endpoint that allows arbitrary provider credit spending.

Phase 6 Scan Engine owns user-triggered execution under quota. Until then,
provider adapters are exercised only through internal/test paths, never via a
public uncontrolled surface.

---

## 8. No Quota/Usage in Adapters

Provider adapters are execution primitives, not policy enforcers.

- Provider adapters do **NOT** call `QuotaService`.
- Provider adapters do **NOT** create `UsageEvent`.
- **Separation of concerns:**
  - The **adapter** knows how to execute ONE request against a provider surface.
  - The **Scan Engine** knows who triggered it, what it was for, and what quota
    applies.

Quota and usage accounting happen above the adapter layer, never inside it.

---

## 9. No Pricing in Phase 5

- **No** hardcoded provider token/search pricing in code.
- Pricing changes independently of code; hardcoding it would silently rot.
- Phase 6 will implement a **versioned pricing snapshot** mechanism.

Until then, cost estimation is out of scope and MUST NOT be approximated inline.

---

## 10. Citation URL Normalization

Citation URLs returned by providers are evidence. Preserve them.

- **Keep** the provider-returned URL intact enough for evidence.
- **Safe basic normalization** allowed: trim surrounding whitespace.
- **Do NOT:**
  - resolve redirects,
  - fetch the URL,
  - strip meaningful query parameters,
  - canonicalize aggressively.

Source analysis (reachability, redirect resolution, content fetch) comes later,
in a dedicated analysis stage, and MUST NOT mutate the stored evidence URL.

---

## 11. Response Text Validation

A nominally successful response that carries **no usable final text** MUST be
treated as an error.

- Raise `ProviderResponseError` when the final answer text is empty/whitespace
  or otherwise unusable after parsing.
- This avoids future false "brand not mentioned" measurements caused by parser
  failure being silently recorded as a genuine negative result.

A missing answer is a measurement failure, not a measurement result.

---

## 12. WEB_GROUNDED Implies Search Actually Occurred

A `WEB_GROUNDED` success **ALWAYS** implies `search_used == True`. This is a
critical methodological invariant for GEO measurement.

- **OpenAI:** `tool_choice` forces `web_search`; if no `web_search_call` is
  present in the response → raise `ProviderSearchError`.
- **Anthropic:** `tool_choice` forces `web_search`; if no `server_tool_use` /
  `web_search_tool_result` is present in the response → raise
  `ProviderSearchError`.
- A `WEB_GROUNDED` result with `search_used=False` would be a **false
  measurement** — it must never be recorded as a successful grounded result.

---

## 13. Anthropic `pause_turn` Is Not a Final Answer

When the Anthropic API returns `stop_reason == "pause_turn"`, the server-side
search loop has reached its iteration limit.

- This is **NOT** a final GEO answer.
- The adapter raises `ProviderSearchError`, **NOT** a successful result.
- **No automatic continuation** is performed by the adapter (a continuation
  would be another billable request).
- Phase 6 Scan Engine owns retry/continuation accounting.

---

## 14. Request ID vs Response ID

`provider_request_id` and `provider_response_id` are **distinct concepts** and
must not be conflated.

- **`provider_request_id`** — HTTP request/support identifier for
  troubleshooting:
  - OpenAI: `x-request-id` header
  - Anthropic: `request-id` header
  - Perplexity: `X-Request-ID` header
  - Google: None (no standard HTTP request ID)
- **`provider_response_id`** — Generated resource/object identifier:
  - OpenAI: response JSON `id` (`resp_...`)
  - Anthropic: message JSON `id` (`msg_...`)
  - Google: interaction JSON `id` (`v1_...`)
  - Perplexity: completion JSON `id`

---

## 15. Provider-Reported Cost

- Perplexity returns a structured **cost object** inside `usage`.
- `provider_reported_cost_usd` preserves this as `Decimal` (not `float` — never
  use floating point for money).
- This is **NOT** our own pricing calculator.
- Phase 6 will decide whether provider-reported cost or our versioned price
  catalog is authoritative.

---

## 16. Malformed JSON Normalization

All four adapters normalize invalid JSON to `ProviderResponseError`.

- `JSONDecodeError`, `ValueError`, and `httpx` internals **never leak through**
  the adapter boundary.
- Tests verify this with genuinely invalid JSON bodies.

---

## 17. Output Token Limits

All four adapters transmit `max_output_tokens` where supported.

- This is a **consistency requirement for measurement reproducibility**.
- Without bounded output, response length variance between providers would
  confound cross-provider comparison.
